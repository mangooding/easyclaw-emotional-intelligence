# GitHub 同步协议

## 1. 目标

以 GitHub 作为 ECS 的远端备份、版本历史和审批界面，实现安全、幂等、可恢复的双向同步。

## 2. 分支模型

- `master`：当前稳定规范与已批准人格。
- `ecs/draft-*`：人格或记忆候选变更。
- `ecs/sync-*`：自动同步与冲突解决。
- `ecs/release-*`：发布准备。

所有自动写入默认创建分支和草稿 PR，不直接写入 `master`。

## 3. 同步触发

连接器可以由以下事件触发：

- 会话开始前拉取；
- 会话结束后生成候选更新；
- 手动执行；
- 定时任务；
- GitHub webhook 收到更新。

调度属于外部运行环境，不由单次聊天会话假装持续执行。

## 4. 拉取流程

1. 获取远端默认分支 HEAD；
2. 校验 allowlist 仓库和路径；
3. 下载清单与相关文件；
4. 验证 schema、文件哈希和版本；
5. 与本地基线比较；
6. 无冲突则更新缓存；
7. 有冲突则生成报告并保持旧稳定快照。

## 5. 推送流程

1. 将会话结果转换为结构化 change set；
2. 运行敏感信息、秘密和提示注入检查；
3. 对照当前远端 HEAD 再次计算 diff；
4. 创建唯一分支；
5. 写入文件并提交；
6. 创建草稿 PR，说明来源、理由、风险和测试；
7. 经人工批准后合并；
8. 记录新的 stable SHA。

## 6. 幂等与去重

每个 change set 使用由规范化内容、来源和目标版本生成的唯一 ID。连接器在写入前检查该 ID 是否已存在，避免重试造成重复提交或重复记忆。

## 7. 冲突策略

- 不同 ID 的结构化记忆可合并。
- 同一 ID 的字段冲突按时间和来源生成候选，不自动裁决。
- Soul、Persona、Relationship 和 Boundaries 的文本冲突必须人工处理。
- 删除与修改冲突时默认保留修改副本，并请求确认删除意图。

## 8. 权限

推荐 GitHub App 或细粒度 token，仅授予目标仓库：

- Contents: Read and write
- Pull requests: Read and write
- Metadata: Read

不需要管理权限。令牌通过环境变量或秘密管理器注入，不写入仓库。

## 9. 失败恢复

- 网络失败：指数退避并保持本地队列。
- 权限失败：停止重试并输出所需权限。
- 远端前进：重新基于最新 HEAD 创建变更。
- PR 被拒绝：标记 change set 为 rejected，不重复自动提交。
- 文件损坏：回退最近已验证 tag 或 SHA。

## 10. 审计

每次同步记录：时间、执行者、源 SHA、目标 SHA、change set ID、修改路径、结果和错误。日志不得包含秘密或高敏明文。
